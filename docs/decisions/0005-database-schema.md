# 0005 — Database schema

- **Status:** Accepted
- **Date:** 2026-09-28
- **Builds on:** [0004](0004-data-files-are-the-source-of-truth.md)

## Context

The API needs to answer questions the data files can't answer quickly on their own: the timeline across titles, a title's play order, an entity with everything connected to it, side-by-side comparisons, graph neighbourhoods and search. The blueprint sketched a table per entity kind (`EventVersion`, `CharacterVersion`, …) and a `differences` table pointing at "any entity", which the database couldn't check.

## Decision

**The database is a derived, disposable copy of `data/`.** `pnpm db:seed` validates the data, then replaces every row in one transaction. Nothing is edited in the database directly.

Schema (PostgreSQL 18, Drizzle ORM, `packages/db/src/schema.ts`):

- **One `entities` table** for every kind, so every reference to an entity is a real foreign key. Only events have extra fields, in `events`.
- **`appearances`** keyed by (entity, title, world), with **`depictions`** beneath them — the model in `docs/model/appearances.md`, one row per fact.
- **Composite foreign keys enforce the model's rules.** A difference must point at two appearances that exist (`differences_from/to_appearance_fk`); a relationship's evidence in a title must point at appearances of _both_ endpoints in that title and world (`edge_titles_source/target_appearance_fk`). The validator checks these too, so they're enforced twice.
- **Relationships are split in two:** `edges` holds the relationship itself; `edge_titles` holds each title's evidence for it (relationships.md §3). Edge IDs are a hash of (source, type, target, from), so the identity rule is the primary key.
- **Reference data is stored too** — titles and their chapters (copied from the shared package), original segments, coverage (also expanded to one row per covered segment), arcs, eras and worlds — so queries can join on it.
- **Derived columns, resolved at seed time:** event years as integer bounds for sorting (chronology.md §2); each appearance's and depiction's `play_position` (chronology.md §7); each entity's `og_segment_id` for coverage-based statuses.
- **Statuses are derived in TypeScript, not SQL.** The comparison query loads the coverage index from the database and calls the shared package's `displayStatus`, so there is exactly one implementation of appearances.md §3.
- **Search** combines `pg_trgm` trigram matching on names and aliases (typos) with full-text search over entity and appearance summaries, plus matches through related entities' names. Every word must match; exact and prefix name matches rank first.
- **Migrations** are generated by drizzle-kit from the schema. CI fails if the schema and the committed migrations drift apart.
- **Local database** runs in Docker on host port **5433**, so it can sit alongside other projects' Postgres on 5432.

## Consequences

- ✅ The database rejects a difference or relationship that doesn't match existing appearances, even if a bug slipped past the validator.
- ✅ Every query is tested against the same answer computed straight from the data files — timeline order, statuses, neighbourhoods — so SQL and TypeScript can't silently disagree.
- ✅ Re-seeding is safe at any time; tests reseed freely.
- ❌ Attributes that reference entities (`killed.in`, relationship `from`/`until` event references) live in JSON, so only the validator checks them.
- ❌ Local development needs Docker. `pnpm check` doesn't: database tests run separately (`pnpm test:db`) and in their own CI job.
